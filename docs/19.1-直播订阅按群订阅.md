# 19.1 直播订阅按群订阅与群管理员权限（增量变更）

> 基线：`docs/19-当前交接文档.md`（v0.9.0 + 娱乐功能增量）｜ 更新：2026-11-13
>
> 本文记录 2026-11-13 对直播订阅的增量修改：**按群订阅**、**群管理员权限**、
> 订阅清单清理、旧表迁移和帮助文案修复。

## 1. 变更摘要

| 项目 | 变更前 | 变更后 |
| --- | --- | --- |
| 订阅范围 | 全局订阅：A 群添加，B/C 群也生效 | **按群订阅**：A 群添加只在 A 群推送 |
| 数据结构 | `live_subscriptions(uid PRIMARY KEY)` | `live_subscriptions(uid, group_id)` 复合主键 |
| 推送目标 | `CHAT_GROUPS` 内所有群 | 只发给**实际订阅了该 UID 的群** |
| 管理权限 | 群主 + SUPERUSERS | **群主 + 群管理员 + SUPERUSERS** |
| 列表 | 所有群共享一份 | 只显示本群订阅 |
| 添加时直播中 | 抑制两个群 | 只抑制当前群 |
| 订阅上限 | 全局 50 | **单群** 50（`LIVE_MAX_SUBSCRIPTIONS`） |
| 旧数据 | — | 旧全局表迁移为 `live_subscriptions_global_legacy`，不自动分群 |
| 线上清单 | 3 条订阅 | 已清空（0 条） |

## 2. 需求

用户确认的新业务流程：

1. A 群群友订阅一个直播，该直播**只在 A 群广播**，不会在 B/C 群广播；
2. 同一个 UID 可以被多个群分别订阅，每个群独立推送、独立去重；
3. 能管理订阅的人不仅包括 SUPERUSERS 和群主，还包括**群管理员**；
4. 先把现有订阅清单清理干净，再切换新逻辑。

## 3. 行为细节

### 3.1 添加订阅

- `/直播订阅 添加 <B站UID>` 只在当前群生效。
- 同一个群内同一个 UID 不能重复添加；不同群可以分别添加。
- 添加时校验 UID、直播间、单群上限。
- 如果主播**正在直播**：只为当前群写入 `suppress` 记录，本次不推送；
  下次真正开播再提醒本群。其他群已有订阅不受影响。
- 返回文案明确写“只在本群提醒”。

### 3.2 删除订阅

- `/直播订阅 删除 <B站UID>` 只删除当前群的订阅，不影响其他群。
- 如果该 UID 在所有群都没有订阅了，才删除共享的 `live_states` 行。
- 通知记录保留（历史去重用途）。

### 3.3 列表 / 查询

- `/直播订阅 列表` 只返回**本群**订阅；标题为“本群直播订阅”。
- `/直播订阅 查询 <B站UID>` 仍是即时状态查询，不写订阅。
- 普通群友可以列表/查询；添加/删除仍需群主、群管理员或 SUPERUSERS。

### 3.4 轮询与通知

- 读取所有群的订阅，按 UID 去重后向 B 站批量查询一次。
- 同一个 UID 被多个群订阅时，只更新一份共享状态，按群分别生成通知。
- 通知去重键仍是 `(uid, group_id, session_key)`；同一场直播每个群只推一次。
- 添加时正在直播、首次观察、场次标识变化等抑制逻辑都按“该 UID 的所有订阅群”处理。
- 接口失败/缺数据仍不会误判下播。

### 3.5 群白名单

- 直播命令仍只在 `CHAT_GROUPS` 内的群可用。
- `poll_once()` 只处理 `group_id` 在 `CHAT_GROUPS` 内的订阅。
- 把群移出 `CHAT_GROUPS` 后：
  - 该群已有订阅保留，但停止推送；
  - 不能再用 `/直播订阅` 命令；
  - 重新加回后恢复。
- 订阅本身按群存储，不再有“新增群自动继承其他群订阅”。

## 4. 数据库与迁移

### 4.1 新结构

```sql
live_subscriptions (
    uid TEXT NOT NULL,
    group_id INTEGER NOT NULL,
    room_id TEXT NOT NULL DEFAULT '',
    uname TEXT NOT NULL DEFAULT '',
    added_by INTEGER NOT NULL DEFAULT 0,
    added_at REAL NOT NULL,
    enabled INTEGER NOT NULL DEFAULT 1,
    PRIMARY KEY (uid, group_id)
);
CREATE INDEX idx_live_subscriptions_group ON live_subscriptions(group_id);

live_states (uid PRIMARY KEY, ...);          -- 按 UID 共享
live_notifications (uid, group_id, session_key, ...); -- 按群去重
```

### 4.2 旧全局表迁移

- 初始化时检测 `live_subscriptions` 是否有 `group_id` 列。
- 旧表没有 `group_id` → 重命名为 `live_subscriptions_global_legacy`，然后创建新表。
- 旧全局订阅无法判断属于哪个群，**不会自动迁移**；需要按群重新订阅。
- 启动日志会出现一次警告：

```
直播订阅已切换为按群订阅；旧全局订阅表保留在 live_subscriptions_global_legacy，
旧订阅不会自动分配到群，请按群重新订阅
```

## 5. 权限

| 操作 | 允许角色 |
| --- | --- |
| 添加/删除订阅 | 群主（`sender.role == "owner"`）、群管理员（`"admin"`）、SUPERUSERS |
| 列表/查询 | 群内所有人 |
| 权限判断位置 | `plugins/live_watch.py` 的 `_is_group_manager()` + `_is_superuser()` |
| 管理范围 | 只能管理当前群；群管理员不能改其他群 |

说明：群管理员权限依赖 OneBot 事件里的 `sender.role`；如果协议端未提供角色，
只能由群主/SUPERUSERS 管理。

## 9. 测试与验收

- 全量测试：**403 passed**。
- 直播相关测试重点：
  - 同一个 UID 在 A/B 群分别订阅；
  - A 群订阅不会通知 B 群；
  - 添加时直播只抑制当前群；
  - 删除 A 群不影响 B 群；
  - 群管理员允许、普通成员拒绝；
  - 列表只返回本群；
  - 群不在 `CHAT_GROUPS` 时订阅暂停推送；
  - 旧全局表迁移；
  - 重启后不重复推送。

建议人工验收：

1. A 群 `/直播订阅` → 确认帮助文案是“只在本群生效”。
2. A 群 `/直播订阅 添加 <UID>`；B 群 `/直播订阅 列表` → 不应看到 A 群订阅。
3. 主播开播后只有 A 群收到卡片；B/C 群不收到。
4. 群管理员（admin）添加/删除 → 成功；普通成员 → 被拒绝。
5. B 群添加同一个 UID → 两个群各自推送、互不影响。
6. A 群删除 → B 群订阅仍保留。
7. A/B 群都不再需要该主播时，注意 A 群的删除不会影响 B 群。

## 10. 回滚与注意事项

- 当前线上订阅为空，所有主播都需要重新按群添加。
- 直播命令仍受 `CHAT_GROUPS` 限制；新增群要加入 `CHAT_GROUPS` 并重启。
- 本次改动已提交 Git 并推送 GitHub（`main`）；未打新版本 tag。
