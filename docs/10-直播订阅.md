# B站直播订阅（v4）

> 版本：v0.7.0 ｜ 状态：已部署线上，待群内验收 ｜ 更新：2026-10-25
>
> 目标：在群里订阅 B 站主播 UID，主播开播时推送**图片卡片 + 文字直播间链接**。
> 只做 B 站，只做“开播提醒”，不做下播提醒。
>
> **2026-11-13 更新**：订阅已改为**按群隔离**，权限扩展为群主/群管理员/SUPERUSERS；
> 详细变更记录见 [docs/19.1-直播订阅按群订阅.md](19.1-直播订阅按群订阅.md)。

## 1. 需求与已确认规则

| 项目 | 规则 |
| --- | --- |
| 平台 | 只做 B 站 |
| 订阅范围 | **按群订阅**：A 群添加/删除只影响 A 群，不会广播到 B/C 群；同一 UID 可在多个群分别订阅 |
| 推送目标 | 只推送到实际订阅了该 UID 的群（命令仍只在 `CHAT_GROUPS` 群可用） |
| 通知时机 | 只推开播；`live_status == 1` 才算直播中 |
| 管理权限 | 群主 + 群管理员（OneBot `sender.role` 为 `owner`/`admin`）+ `SUPERUSERS` 可添加/删除 |
| 普通群友 | 可以看 `列表` 和 `查询`，有简单限频 |
| 添加时正在直播 | 抑制当前场次，只回复“当前正在直播”；下次真正开播再推 |
| 轮询间隔 | 默认 **180 秒**，可配置 |
| 推送形式 | HTML + Playwright 渲染卡片；同一消息内附文字直播间链接 |
| 图片体积 | 目标 350 KB，超过自动降质量；硬上限 600 KB，仍超则回退纯文字 |
| 存储 | 独立 SQLite `data/live.sqlite3`，不引入 MySQL/Redis |
| 失败处理 | 接口失败只退避重试，**绝不**当成下播；单群发送失败不影响另一个群 |

## 2. B 站接口实测（2026-10-25）

### 2.1 之前“程序访问不到”的根因：User-Agent 被 412

用项目同款 `httpx 0.28.1` 在本机和线上服务器分别测试：

| 请求头 | 结果 |
| --- | --- |
| `httpx` 默认 UA（`python-httpx/0.28.1`） | **HTTP 412**，返回 B 站拦截页 |
| Chrome UA + `Referer: https://live.bilibili.com/` | **HTTP 200**，正常 JSON |

线上服务器 `39.106.135.148` 上连续 3 次批量查询也全部 200，单次约 0.1 秒。
所以不是服务器网络、DNS、SSL，也不需要登录、Cookie 或 WBI。

另外两个容易踩的坑：

- 批量参数必须是 `uids[]=UID1&uids[]=UID2`；写成 `uids=1,2` 会返回
  `code=1 invalid params`。
- 直播列表/搜索类接口（例如部分 `xlive/web-interface/v1/index/getList` 参数、
  `api.bilibili.com/x/web-interface/search`）会返回 `-352` 或 412，需要 WBI/Cookie；
  本项目不使用这类接口。

### 2.2 批量状态接口（主接口）

```
GET https://api.live.bilibili.com/room/v1/Room/get_status_info_by_uids?uids[]=UID1&uids[]=UID2
```

返回 `data` 是以 UID 为 key 的 map；全部 UID 都无效时是 `[]`，解析要兼容两种形态。

| 字段 | 含义 |
| --- | --- |
| `live_status` | `0` 未开播，`1` 直播中，`2` 轮播/录播 |
| `live_time` | Unix 秒；直播中非 0，未开播为 0。用作“场次 ID” |
| `room_id` | 直播间号 |
| `uname` | 主播名 |
| `title` | 直播间标题 |
| `cover_from_user` | 封面图 |
| `online` | 在线人数 |

实测：

- 300 个 UID 一次请求也能正常返回；实现按 100 个分片。
- 无效/没有直播间的 UID 会被省略，不会返回错误。
- `live_time=1792912598` 对应北京时间 `2026-10-25 15:16:38`。
- 封面 CDN 在本地与服务器都能直接下载，约 100 KB。

### 2.3 单 UID 查房间（备用）

```
GET https://api.live.bilibili.com/room/v1/Room/getRoomInfoOld?mid=UID
```

返回 `roomStatus`（1=有房间）、`liveStatus`（0/1）、`roomid`、`title`、`cover`、
`online`、`url`。当前实现只用批量接口；这个接口保留作排障/换源参考。

> 注意：`getRoomInfoOld` 会把 `live_status=2` 的轮播返回成 `liveStatus=0`，
> 所以判断“是否直播中”必须以批量接口的 `live_status == 1` 为准。

## 3. 代码结构

```

deltaforce_bot/models/live.py               # LiveStatus / LiveState / LiveSubscription / LiveNotification

deltaforce_bot/render/templates/live_notification.html.j2
plugins/live_watch.py                       # 命令入口 + 180s 轮询 + 卡片/文字推送
scripts/render_live_preview.py              # 本地预览卡片
data/live.sqlite3                           # 运行时生成，已 gitignore
```

`Runtime` 只在 `LIVE_ENABLED=true` 时创建直播对象；初始化失败只关闭直播功能，
不影响卡战备/聊天/每日密码。`Runtime.aclose()` 会关闭 B站客户端与 SQLite。

## 4. 存储

三张小表，WAL 模式，`cache_size` 限制在约 2 MB：

```sql
live_subscriptions(
    uid TEXT, group_id INTEGER,
    room_id TEXT, uname TEXT,
    added_by INTEGER, added_at REAL, enabled INTEGER,
    PRIMARY KEY(uid, group_id)
)

live_states(
    uid TEXT PRIMARY KEY,
    room_id TEXT, uname TEXT,
    live_status INTEGER, live_time INTEGER,
    title TEXT, cover TEXT, online INTEGER,
    checked_at REAL, missing_count INTEGER
)

live_notifications(
    uid TEXT, group_id INTEGER, session_key TEXT,
    kind TEXT,          -- push / suppress
    notified_at REAL,
    PRIMARY KEY(uid, group_id, session_key)
)
```

- `session_key` 优先用 `live_time`；缺失时退回固定值 `live`，并在下播时清掉对应记录。
- `live_notifications` 保证“同一场直播、每个群只推一次”；每个订阅群各自一条记录。
- 旧版本全局订阅表在初始化时会重命名为 `live_subscriptions_global_legacy`，
  旧订阅不会自动分配群，需要按群重新订阅；当前线上清单已清空。
- 通知记录保留 30 天（`LIVE_HISTORY_DAYS`），启动时清理。
- 不把封面/渲染图存数据库；图片只在发送时临时下载、渲染、发送。

预计 50 个订阅 + 30 天通知记录不超过 1 MB，不会给云服务器造成存储压力。

## 5. 轮询与通知逻辑

每 180 秒执行一次 `poll_once()`：

1. 读取全部群的订阅，UID 去重后批量查询 B 站；
2. 更新每个 UID 的最新状态；
3. 对“当前直播中”的 UID，为每个实际订阅了该 UID 的群检查 `(uid, group_id, session_key)` 是否已推送；
4. 未推送的生成 `LiveNotification`，由插件渲染卡片并发送；
5. 发送成功后写入通知记录；失败不写，下一轮重试。

关键边界：

- **只推 1**：`live_status=0/2` 都不推；轮播不算开播。
- **添加时正在直播**：只为当前群写入 `kind=suppress` 记录，不会影响其他群。
- **首次观察**：数据库里没有状态记录时只保存状态，不补推，避免启动刷屏。
- **重启**：状态和通知记录在 SQLite，重启后不会重复；若重启前是未开播、重启后已开播，
  会正常补推一次。
- **同一场直播 `live_time` 变化**（断流重连等）：按同一场处理，抑制新场次，避免重复。
- **接口失败/超时/412/-352**：不更新状态、不发通知；轮询指数退避（最长 15 分钟），
  日志节流。
- **UID 从结果里消失**：连续 3 次才按未开播处理，避免临时缺数据误判。
- **多群**：一个群发送失败只重试该群；另一个群成功记录后不会重复。
- **bot 未连接**：跳过发送，不写记录；连上后的下一轮重试。
- **卡片/图片发送失败**：同一轮立即回退纯文字；文字里始终有直播间链接。

## 6. 命令与权限

```
/直播订阅 添加 <B站UID>
/直播订阅 删除 <B站UID>
/直播订阅 列表
/直播订阅 查询 <B站UID>
```

- 必须带 `/` 或全角 `／` 前缀；聊天插件会把它识别为命令，不会让 LLM 接走。
- 添加/删除：群主、群管理员 + `SUPERUSERS`；普通群友不允许。
- 列表/查询：群内所有人可用；列表只显示本群订阅。
- 订阅按群隔离，回复会明确说明“只在本群提醒”。
- 添加时校验 UID：纯数字、大于 0、有直播间；无直播间直接拒绝。
- 同一个 UID 可以在多个群分别订阅；同一个群内只能订阅一次；单群上限 `LIVE_MAX_SUBSCRIPTIONS`（默认 50）。
- 添加/删除/查询有每用户/每群限频，`DEBUG_GROUPS` 内免限流。
- 查询只返回文字状态，不写订阅。

## 7. 卡片与压缩

原型：`assets/items/html_prototype/直播订阅原型.png`。

版式：

- 顶部：`主播名 -- 直播中`，状态用 B 站粉色 `#FB7299`；
- 中间：16:9 圆角封面；封面下载失败显示「未成功获取封面」；
- 底部：直播间地址；
- 卡片宽 720px，白色卡片 + 浅灰页面背景。

渲染链路复用现有 `CardRenderer`：

```
Jinja2 模板 → 本地 HTML 文件 → Playwright 打开 → JPEG 截图
```

压缩策略：

- 先按 720px 宽、JPEG 质量 86 渲染；
- 超过 `LIVE_IMAGE_MAX_KB`（默认 350 KB）时依次降到 78/70/62；
- 仍超过 350 KB 但低于 600 KB，使用最小的那张；
- 超过 600 KB 放弃图片，回退纯文字。

实测：带封面卡片约 **58 KB**，无封面占位卡片约 **19 KB**。
同一场直播、多个订阅群复用同一份图片字节，不重复渲染。

推送消息：**一条消息内**包含卡片图片 + 文字 `【B站开播】主播名 / 标题 / 直播间：URL`；
这样图片和链接要么一起成功，要么回退文字，不会出现“图片发了、链接没发”的部分状态。
图片发送失败时立即改发纯文字。

## 8. 配置

```dotenv
LIVE_ENABLED=false
LIVE_DB_PATH=data/live.sqlite3
LIVE_POLL_INTERVAL=180       # 秒；最小生效值 60
LIVE_TIMEOUT=15
LIVE_MAX_SUBSCRIPTIONS=50
LIVE_HISTORY_DAYS=30
LIVE_IMAGE_MAX_KB=350
LIVE_RATE_USER=5             # 次/分钟
LIVE_RATE_GROUP=20
LIVE_USER_AGENT=             # 留空使用内置 Chrome UA
```

- 推送目标直接复用 `CHAT_GROUPS`，不新增群白名单。
- `CHAT_GROUPS` 为空时直播订阅不会推送，启动日志会告警。
- `LIVE_USER_AGENT` 不要改成非浏览器 UA；B 站会返回 HTTP 412。

## 11. 已知限制 / 风险

- B 站接口是非官方公开接口，可能改字段、限流或风控；适配层隔离，改接口只改
  `adapters/live_bilibili.py`，并用 fixture 锁定字段。
- 机房 IP 理论上可能被 B 站风控；已用浏览器 UA + 低频（180 秒）降低风险。
  若长期 412，可评估增加匿名 `buvid3` Cookie 或换请求实现，但不建议为此引入重依赖。
- 轮询间隔决定通知延迟，最坏约 3 分钟；不接受可把 `LIVE_POLL_INTERVAL` 调到 60。
- 只推开播，不推下播；如需下播提醒需要新增状态与文案。
- `live_status=2`（轮播）不算开播，不会推送。
- 按群订阅：每个群的订阅列表独立，A 群订阅不会在 B/C 群广播；
  同一个 UID 可被多个群分别订阅，每个群各自去重。
- 卡片图片里的链接不可点击，所以额外附了文字链接；如果以后加二维码，可减少文字依赖。
- 极端情况下“发送成功但写通知记录前进程崩溃”会导致重启后重复推送一次；可接受。
