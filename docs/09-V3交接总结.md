## 0. 一句话现状

QQ 群机器人已具备三块线上能力：**卡战备图片卡片**、**LLM 群聊 + 本地表情包**、
**每日密码（图片卡片、0:15 预热、11:00 推送）**。代码在 GitHub `Mengyks/DeltaForceQQbot`，

> **注意版本差异**：服务器当前运行的是 2026-10-24 部署的代码，包含每日密码的图片/预热/推送；

### 1.1 卡战备

- GitHub/本地最新代码要求斜杠：`/卡战备 巴克什 绝密`；`/凑战备` 同样必须带斜杠。
- 服务器当前仍是旧解析器（`卡战备 ...` 和 `#卡战备 ...` 也还能触发），**下次部署后统一为严格斜杠**。
- `兑换` 是唯一可选项；`/凑战备` 默认关闭（`CUSTOM_ENABLED=false`）。
- 数据按 `lv` 缓存 4 小时；图片按“档位 + 方案签名 + 更新时间”缓存，发送成功后才写缓存。
- 渲染失败自动回退文字；缺图渲染灰色占位块。
- 地图/难度/别名配置在 `config/gates.json`；不需要改代码。

### 1.2 群聊

- 只处理群聊，不处理私聊；群白名单 `CHAT_GROUPS`。
- 立即触发：@ 机器人、引用机器人消息、文本包含 `CHAT_ALIASES` 任一别名。
- 跟进窗口：机器人成功回复后 `CHAT_FOLLOWUP_WINDOW=180` 秒；窗口内最多再回
  `CHAT_FOLLOWUP_MAX_REPLIES=3` 次，两次至少间隔 `CHAT_COOLDOWN=20` 秒。
- `CHAT_AMBIENT_ENABLED=false`（当前不主动插话）。
- 群共享上下文写 `data/chat.sqlite3`，默认保留 7 天；不是只记录被 @ 的消息。
- 当前消息里的 `image`/`mface` 会尽量作为视觉输入；历史图片只存 `[图片]`。
- 模型输出按换行/句末标点拆成最多 3 条独立消息；不使用 QQ 引用回复。
- 人格文件 `config/persona.md`（当前 wudian），按 mtime 热加载。
- 清理指令只有 `SUPERUSERS` 可用；群主/管理员无权限。

### 1.3 每日密码

- 每天 **00:15** 预热当天缓存；**11:00** 推送到白名单群；11:00 后有 60 分钟补推窗口。
- 群友发 `/每日密码` 直接复用当天缓存，每群 5 分钟最多触发一次；返回图片卡片，失败回退文字。
- 同一天只向免费源取一次；快照按北京时间自然日缓存，跨天重新取。
- 主源 4399 游戏盒（有地点说明/配图），失败换 eleven.icu（只有密码，无地点说明）。
- 推送去重、快照都存在独立的 `data/daily_password.sqlite3`；同一天每群只成功推一次。
- 卡片为六地图背景 + 大号密码，JPEG 质量 90，约 217 KB（避免 OneBot 单帧 1 MB 限制）。
- 详细规则、接口实测和验收见 `docs/08-每日密码.md`。

## 6. 已知问题 / 事故记录

1. **2026-10-25 11:00 没有推送每日密码**
   - 原因：服务器 `.env` 的 `DAILY_PASSWORD_PUSH_ENABLED=false`。
   - 根因：旧版 `deploy_server.py` 默认上传本地 `.env`；本地为了防双推设了 `false`，
     部署时覆盖了服务器配置。服务一直运行，所以推送任务从未启动。
   - 修复：服务器改为 `true` + `PUSH_TIME=11:00` 并重启；v0.6.1 起部署脚本默认保留服务器 `.env`，
     需要覆盖时才加 `--upload-env`。
2. **4399 在 00:05 返回 `code=-1`**
   - 4399 工具页自身在 0:06–0:10 才刷新；0:05 预热会退化到 eleven（没有地点说明）。
   - 已将预热改为 **00:15**（代码默认、服务器 `.env`、文档、测试全部同步，v0.6.2）。
   - 次日 00:15 后应优先拿到 4399 完整数据；若 4399 仍失败仍会自动换 eleven。
3. **同一天只用一份源**
   - 一旦当天用 eleven 取到，按“一天只取一次”规则用到当天结束，不会因为 4399 稍后恢复而升级。
   - 如果非常在意地点说明，可评估“备用源升级”逻辑，但会增加一次上游请求。
4. **免费源稳定性**
   - 两个源均非官方，可能改字段/限流/停服；已有 fallback 和契约测试，但仍需关注 4399 的可用性。
5. **服务器与 GitHub 版本差**
   - 下次部署前先确认服务器 `.env`；部署脚本默认保留它。部署后再确认 `/卡战备` 严格斜杠已生效。
6. **资源不入库**
   - `assets/items`、`assets/memes`、`.env`、`data/` 都不在 Git；换机/重装需重新上传资源。
7. **图片体积**
   - 每日密码卡用 JPEG 约 217 KB，避免 1 MB PNG 转 base64 超过 OneBot 单帧限制；
     卡战备图片仍是 PNG。

## 7. 下一版规划

建议作为 **v0.7.0**，两个功能独立成模块，互不共享数据库，不修改现有卡战备/聊天/每日密码行为。
推荐先做**制作台利润**（数据源和客户端已成熟），再做**直播订阅**（平台接入不确定性更高）；
如果并行，也保持两个独立的 service/plugin/调度与存储。

### 7.1 制作台利润

**目标**：查询特勤处制造台（技术中心/工作台/制药台/防具台）当前推荐制造产物及利润。

**数据源决策（必须先确认）**：

- Pro 版 `422150879e0`：自有源计算，优先候选；
- 官方数据版 `396183651e0`：平台标注“不准”，是否展示/是否作为兜底需确认；
- 先录一份真实响应，确认字段、利润口径、刷新频率和每次请求消耗的资源次数；
- 复用 `OrziceClient` 的缓存/额度/错误映射，不新建 HTTP 客户端；
- 若接口成本较高，缓存建议 1~4 小时，并接入 `ORZICE_DAILY_QUOTA`。

**建议结构**：

```
adapters/crafting.py（或直接扩展现有 OrziceClient 调用）
models/crafting.py
services/crafting.py
plugins/crafting.py
tests/test_crafting.py
tests/fixtures/real/crafting_*.json
```

**待确认**：

1. 用 Pro 版还是官方版？两者都展示，还是只展示 Pro？
2. 利润口径：售价 − 材料成本？是否扣税/手续费/制作时间？
3. 展示哪些制造台和产物数量？按利润排序还是按制造台分组？
4. 命令名和格式（例如 `/制造利润`、`/特勤处`），是否支持指定制造台？
5. 返回文字还是图片卡片？若卡片，可复用 `CardRenderer` + 新模板。
6. 哪些群可用、是否限流、缓存多久、每日数据源预算。
7. 是否允许群友手动查询，还是只做定时推送？

**验收**：

- 真实响应契约测试锁定字段和利润等式；
- 同一参数缓存命中不重复消耗额度；
- 数据源错误/无权限/额度熔断有友好提示；
- 卡战备、聊天、每日密码测试全部保持通过；
- 真机群内查询结果与数据源页面一致。

### 7.2 直播订阅

**目标**：订阅指定主播/房间，开播时推送到群；只做“是否开播”状态查询与提醒。

**平台范围（必须先确认）**：

- B 站：公开状态接口可行性最高，建议作为第一版范围；
- 抖音/斗鱼/虎牙：接口、签名、Cookie、风控和维护成本需要先验证，不建议首版全接；
- 需要用户提供具体主播/房间号、目标群、平台优先级；
- 明确“只查状态、不抓直播内容”，遵守平台条款与频率限制。

**建议结构**：

```
adapters/live/<platform>.py       # 平台适配：查房间状态，统一成 LiveStatus
models/live.py                    # Subscription / LiveStatus / Notification
services/live_watch.py            # 订阅 CRUD、状态变化检测、去重
plugins/live_watch.py             # 订阅命令 + 轮询调度
data/live.sqlite3                 # 独立 SQLite（订阅、状态、已通知记录）
tests/test_live_*.py
```

**推荐行为**：

- 轮询间隔 1~5 分钟（先默认 2 分钟），每个平台独立适配、独立超时；
- 只在“离线 → 开播”边沿通知一次；同一场直播不重复；下播后可再次触发；
- 通知内容：平台、主播名、标题、开播时间、房间链接；可选配图/封面；
- 订阅持久化，重启不丢；通知记录持久化，避免重启重复推送；
- 轮询失败指数退避/限频，日志节流；不影响其他功能；
- 订阅管理权限（建议 `SUPERUSERS` 或群管理员，需确认）；
- 目标群只允许白名单群；是否 @全体成员必须确认，默认不发。

**待确认**：

1. 平台：先只做 B 站，还是同时做多平台？
2. 主播列表、房间号/UID、目标群？
3. 谁可以添加/删除订阅？群友自助还是管理员？
4. 轮询频率、失败重试、通知模板、是否 @全体？
5. 是否需要“正在直播”列表/手动查询，还是只做开播通知？
6. B 站是否需要 Cookie/WBI 签名；抖音等是否需要第三方签名服务（尽量不引入）。

**验收**：

- 添加订阅 → 开播后只通知一次；重复轮询不重复；
- 下播再开播 → 再次通知；
- 服务重启 → 订阅和已通知状态保留；
- 平台接口失败 → 有节流日志，不刷屏、不阻塞其他任务；
- 非白名单群/无权限用户不能修改订阅；
- 不影响卡战备、聊天、每日密码。

### 7.3 共用约束

- 部署继续走原生 systemd；不要引入 Docker 依赖。
- 新功能单独建 SQLite，不要复用 `chat.sqlite3` 或 `daily_password.sqlite3`。
- 新定时任务与每日密码一样用 `asyncio` 循环，或评估 APScheduler/systemd timer；
  但必须可取消、失败不拖垮主进程。
- 所有外部请求通过 `httpx`，复用现有超时/重试/限流/额度习惯。
- 新数据源先录真实响应进 fixture，再写解析和契约测试。
- 代码改动先给用户看，确认后提交；版本按里程碑递增并打 tag。
